# HANA integration and approved additive update

A read-only live connection succeeded against the configured, confirmed ToolSathi
destination. Inspection found 585 rows across 21 application tables and an exclusive
application schema. `TS-00078` was absent. This is a current observation, superseding
the historical 394-row baseline. Credentials, SQL hostname, account and schema names
were not written into reports.

The user explicitly approved backup and additive HANA update after automatic
approval review initially rejected the sensitive-data export. The approved export
captured all 585 records, verified the canonical per-table manifests, reconstructed
the complete backup in an isolated SQLite database and verified every restored row.
The full backup remains in ignored local `backup/`; only verification metadata is
tracked in `v2.1-backup-verification.json`.

All 14 missing tables were then created, and the reviewed 106 namespaced fixture
records plus one append-only seed audit entry were inserted. No existing table or
record was updated, deleted or reset. All 585 original records match the backup.
The repeat-seed preview finds 106 matching rows and zero proposed inserts.
Final counts are 692 records / 35 tables. Two independent backend starts read the
same persisted seed incident and workforce recommendations. The read-only verifier
also compares all trace serials, tiers, locations, gaps and evidence with the backup;
see `v2.1-hana-verification.json`.

The 14 create-only additions are in `v2.1-hana-additions.sql`; all baseline table
definitions remain unchanged. `scripts/v21-demo.js --hana-apply` requires an existing
backup inside ignored `backup/`, validates its manifest against current records,
checks target/exclusive ownership and existing table compatibility, creates only
missing tables, then transactionally inserts only missing matching V21 fixture rows.
Conflicts reject instead of overwriting. HANA DDL commits individually; this is
explicitly not described as an atomic DDL transaction.

Use root `npm run dev:hana:v21` to run the deployed 35-table HANA application. The
launcher sets `V2_WORKFLOW_ENABLED=true` for its backend child, disables synthetic
startup seeding, and preserves the private `.env`. It never deploys on startup.
Repeating the deployment command requires a fresh verified snapshot of the current
destination; an old pre-deployment backup deliberately fails its stale-backup check.

The stored original HANA fixture uses `2026-11-04T05:12:00.000Z`, while the current
local seed uses `2026-10-31T05:12:00.000Z`. The original import audit and two matching
production runs identify the fixture clock. `/tools` exposes this verified synthetic
scenario time, and the Worker demo loader uses it. No live report time is inferred
from this fixture. Arbitrary report times legitimately produce different trace totals.

SQLite remains explicitly selectable; no HANA connection failure silently changes
database mode. Local fixtures/tests use new files or memory only.
