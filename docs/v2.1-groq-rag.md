# Groq and authorized retrieval

The private environment is loaded on the backend only. `AI_REASONING_PROVIDER`
selects Groq or the existing Sarvam implementation; when Groq credentials exist,
Groq is selected by default. `GROQ_MODEL`, if specified, must be present in the
account's active models response. The verified account selected
`openai/gpt-oss-120b`. Calls use JSON mode with local Ajv schema checks, bounded
timeouts, explicit error codes, and low reasoning effort where supported.

The scoped RAG loader filters records before embedding or context assembly:
Workers receive their own incidents; Technicians receive assigned incidents;
review roles receive authorized manufacturing context. SOP/repair history is
restricted to staff. Existing chunking, source hashes, source versions, passage
IDs, local multilingual embeddings and keyword fallback are reused. Runtime does
not automatically download a model or create a competing vector service.

Generated source IDs must belong to retrieved records. Prompts treat user and
document text as untrusted data; the assistant has no write tools. Inventory,
eligibility, traces and approval outcomes come from deterministic backend queries.
SOP examples remain clearly synthetic/unapproved context.

The live authorized chatbot HTTP check passed with Groq and two sources. The
available runtime used KEYWORD retrieval; semantic embedding inference was not
live-verified. Semantic duplicate adapters and repair guidance retain contract
tests; live accuracy of every diagnostic suggestion is not asserted.

The separate legacy recovery planner retains its existing Sarvam default. Automatic
approval review rejected changing its broader incident-context payload to Groq;
no workaround was used. New V2.1 reasoning routes are unaffected.

References: [Groq models](https://console.groq.com/docs/models),
[structured output](https://console.groq.com/docs/structured-outputs),
[Sarvam STT format/language support](https://docs.sarvam.ai/api-reference/speech-to-text/transcribe).
