## Implementation decisions

- Reuse existing `/v2` services and teammate AI/rules adapters. Never edit their
  owned folders or change deterministic trace calculations.
- Add related extension tables instead of altering the original 35 tables.
  Old HANA deployments remain usable until explicitly enabling the reviewed
  V22 schema. No startup migrations or HANA resets.
- Capabilities are approved server records, separate from identity-provider
  roles. Assigner is a capability on Verifier, not a self-selected new privilege.
- Legacy routes remain available. New pages use incident URLs and the existing
  client, speech component, workflow and exposure services.
- Functional screens and lifecycle tests precede visual polish. README is last.

## B–E verification checkpoint

New routes `/worker`, `/manager`, `/technician`, `/verifier`, `/issues`,
`/issues/:incidentId`, `/notifications`, `/profile`, `/login`, `/register` use
persisted APIs. Legacy screens remain available. The issue detail connects
assignment, conversations, duplicate review, repair and existing approvals.
Demo identity survives refresh; production identity still uses XSUAA.

Manager/Verifier scope is enforced against approved work centers. Verifier
assignment requires an explicit administrator-approved capability; verification
is a separate capability. Assignment and reassignment share the original API.
Reassignment requires the current work-order ID and reason, and refuses to
discard started repair evidence or active reservations. Blockers, additional
evidence requests, corrections and failed independent inspection are audited.
Corrected work returns to Under repair; prior readings remain in appended
evidence/audit records. Verification rejects conflicting assignment/review actors.
